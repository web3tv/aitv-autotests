# Нагрузочные тесты (k6) — PoC

Отдельный слой от Playwright: k6 стреляет по HTTP напрямую, браузер не поднимается.
Папка не входит в `testDir` Playwright и в обычных прогонах не участвует.

## Требования

- `brew install k6`
- VPN до дев-стендов (та же сеть, что и для Playwright-тестов)

## Запуск

```bash
npm run load:smoke                     # 5 VU / 30s на dev2 — проверить, что сценарий жив
npm run load                           # 50 VU: 2m разгон + 5m полка + 1m спад
ENV_FILE=.env.web3tv npm run load      # то же на dev1
bash scripts/runLoad.sh load/scenarios/browse.js --summary-export out.json  # доп. флаги k6
```

## Сценарии

- `scenarios/browse.js` — анонимный сёрфинг: главная, публичный листинг `/videos/`,
  карточка случайного видео, страница канала `@qavischan`. Только чтение — стенд не мутирует.
  Профили `smoke` (5 VU) и `load`/`full` (50 VU — синонимы: `load` локально, `full` из CI).
- `scenarios/prodHomepage.js` — нагрузка на главную (прод). Профили `smoke` (10 VU) и
  `full` (100 VU, профиль лида). Регулярно гоняется через `weekly-load.yml`.

## CI: `weekly-load.yml`

Расписание (вс 06:00 UTC) гоняет прод/`smoke`. Вручную (`workflow_dispatch`) можно выбрать
стенд — `prod` / `dev2` / `dev1` — и профиль `smoke`/`full`. Прод запускает `prodHomepage.js`,
dev-стенды — `browse.js` (конфиг берётся из `.env`-файла стенда). Для dev-ранов воркфлоу
сам поднимает WireGuard и встаёт в общую VPN-очередь (`concurrency: wireguard-vpn`).

## Baseline / детект регресса

Норма фиксируется на **серверных, портируемых** метриках, чтобы ловить регресс прода,
а не шум замера:

| Метрика | Что значит | Baseline (прод, 100 VU) | Порог (норма + запас) |
|---|---|---|---|
| `http_req_waiting` (TTFB) | время ответа сервера | med 0.53s · p95 2.64s | med < 1s · p95 < 3s |
| `http_req_failed` | доля HTTP-ошибок | 0% | < 1% |
| `checks` | доля успешных проверок | 100% | > 99% |
| `http_req_duration` | полное время (TTFB + скачивание) | p95 17s | < 60s (справочный) |

**Почему не `http_req_duration` как гейт:** под ним время скачивания 754-КБ главной, которое
упирается в канал раннера (на ноутбуке ~57 Мбит/с), а не в прод. С другой машины/сети эта
цифра невалидна — поэтому она справочная, а регресс ловим по TTFB.

**Как ратчетить:** baseline снимать с фиксированного стенда (GitHub-раннер, `weekly-load.yml`),
не с ноутбука. По мере накопления чистых прогонов из CI ужимать пороги TTFB к реальной норме.
Источник текущих цифр — `load/reports/prod-homepage-20260813-1255.json`.

## Правила

- **Прод не трогаем.** Стенды общие: `load`-профиль гонять в согласованное окно,
  не параллельно с nightly-регрессией.
- Никаких мутаций: не регистрировать юзеров (auth-сервис навсегда резервирует хэндлы),
  не заливать контент. Нагрузочный сценарий = только GET.
